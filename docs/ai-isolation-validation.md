## 확인한 원인과 변경

1. 과거 모델 출력은 인용문을 직접 재작성하면서 줄 번호도 생성했다. 공백·줄바꿈·적용 범위의 차이가 인용 검증 실패로 이어질 수 있었다. 줄 번호 계약에서는 모델이 분류와 행 ID만 선택하고 서버가 원본의 UTF-16 위치와 인용문을 생성한다.
2. 시작 브랜치의 compact 계약은 최대 32개 중요 항목만 선택하고 나머지 전체를 서버가 reference로 채운 뒤 complete=true를 만들었다. 조건 누락과 구조적 범위 검사를 혼동할 수 있었다. 자동 reference 생성과 잘못된 제안의 조용한 삭제를 제거했다. 모델이 모든 내용 행을 항목 또는 명시적 reference 범위로 배정하고 complete를 선언해야 한다. 누락/중복/잘못된 위치/출력 제한은 성공으로 반환하지 않는다.
3. SDK catch가 서버의 INVALID_AGENT_OUTPUT까지 ADAPTER_FAILED로 변환했다. 서버가 만든 안전한 검증 메타데이터는 그대로 전달하고 제공자 오류의 본문은 계속 숨긴다.
4. 검증되지 않은 근거, 다른 직무·지난 구간에서 빌린 근거, 부정·복합 필수/우대·충돌하는 AND/OR는 확인 필요로 남긴다. 한국어 구어체 요건 제목도 AI 계약에서 근거로 인정한다. 일반 웹앱 규칙 분류기는 변경하지 않았다.
5. 명시적 자격요건이 참고정보에 숨겨진 일부 명백한 경우를 차단한다. 이 검사는 일반적인 의미 정확성 증명이 아니며, 원문 전체 의미 누락을 결정적으로 검증할 수 있다는 주장을 하지 않는다.

추가 유료 호출을 멈추고 서버 처리를 다음처럼 수정했다:

- 분류(category), 지원 유형(applicantType), 조건 관계(relation)를 독립적으로 취급한다. 지원 유형의 증거가 없으면 해당 유형을 unclear로 지우고 경고하되, 별도 근거로 확인된 필수·우대 분류를 지우지 않는다.
- 다른 직무/다른 구간의 근거를 빌린 필수·우대 분류나 원문의 명시적 부정은 계속 확인 필요로 남긴다.
- AND/OR 확인은 조건 항목에만 적용한다. 법적 고지·참고정보는 이 검사로 확인 필요로 바꾸지 않는다. 조건 관계가 불확실해도 분류 자체와 혼동하지 않는다.
- 묶인 업무·조건은 원문에서 각 행이 명확한 글머리표로 시작하는 경우에만 분할하고, 이어지는 설명 행은 해당 항목에 보존한다.
- 명시적인 `경력만 해당` 문구는 원문에서 직접 지원 유형 근거를 만든다.
